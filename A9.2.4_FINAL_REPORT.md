## B. Why activity = DISABLED existed

**It was never stored.** `activity` is derived on every read by
`atlas_sem_plan_for`; `DISABLED` came from two lines in `src/sem/schedule.c` —
`!out->auto_rebuild` and an empty compilation-database list. The stored fact was
`sem_repo_config.auto_rebuild`, default 0.

**Classification: deliberate authority design.** Not a leftover, not rollout
safety, not resource protection alone. The primary sources say so in those words:

- `include/atlas/sem.h`, on `atlas_sem_config` — *"The row is also the **authority
  opt-in**, and that is not a secondary use… `auto_rebuild` is false by default
  and only an operator writes the row."*
- `src/sem/schedule.c`, check 2 — *"an operator has not authorised a compiler to
  run over this repository, and A8-CI's rule that no model can cause one to run
  survives A9.2.3 because of this line."*
- Migration 18's comment — *"the migration enables nothing that was not enabled
  before it ran."*

**Does the rationale still hold after A9.2.3?** Partly, and the part that does
not is the part A9.2.4 changes. A9.2.3 added debounce, coalescing, a retry
governor, failure isolation and daemon ownership, so the *operational* case for
refusing by default was already gone. What remained was an authority argument,
and on inspection that argument was about the wrong thing: **what the opt-in
protected was never code execution.** libclang parses repository text; the
compilation database's `command` string is word-split and never executed;
arguments pass a positive allowlist; include directories outside the repository
are recorded and never opened; the parse runs in a bounded child with an empty
environment and an address-space ceiling. The opt-in was authority and *resource*
policy. A9.2.4 replaces it with authority and resource policy rather than
removing it — see D.

## C. Original activation semantics, traced

| Question | A9.2.3 answer |
| --- | --- |
| where stored | `sem_repo_config.auto_rebuild`, INTEGER, default 0 |
| valid states | 0 or 1 — and nothing else, which is the defect |
| default | 0, and **no row at all** for an unconfigured repository |
| at registration | no row is created; `atlas_db_repo_add` writes nothing here |
| pre-A9.2.3 migration | migration 18 created the table empty |
| who may write | operator only: `code sem-config`, and `code.sem_config` in the operator-uid RPC table |
| persistence | durable, in the index |
| at daemon start | nothing; the sweep enumerated *configured* repositories only |
| governor | `fail_count` / `fail_identity`, compared by identity, never by elapsed time |
| on failure | `FAILED` + hold until the source identity moves |
| recovery | automatic, when the inputs change |
| activity vs availability | conflated: `DISABLED` meant *both* "not enabled" and "no compilation database" |
| policy or scheduler state | **policy**, stored, and inseparable from silence |

The last two rows are the findings. `DISABLED` named a policy, a configuration
gap and a missing file with one string; and a stored `0` could not distinguish an
operator's `--no-auto` from nobody ever having said anything.

## D. Selected generic activation policy

**Option C — explicit per-repository policy with a sane default — plus a
root-owned machine-wide default.** Evaluated against A (opt-in forever), B
(inputs available ⇒ enabled), D (enable after first successful build) and E
(always enabled, governor decides when).

```
auto_intent = DISABLED  ->  off, for ever, until an operator says otherwise
auto_intent = ENABLED   ->  on
auto_intent = UNSET     ->  syspolicy.semantic_auto_default
                            (absent ⇒ ATLAS_SEM_AUTO_DEFAULT = ENABLED)
```

`atlas_sem_auto_effective` is the whole policy in one pure function, so the
daemon, the CLI and every status surface answer identically because they call it
rather than because three copies are kept in step.

**Why not B.** "Inputs available ⇒ enabled" cannot express an operator's
refusal at all, so a machine where a compiler must not run has no answer.
**Why not D.** "Enable after the first successful build" makes the first build
the thing somebody has to remember, which is the same problem one step along.
**Why not A.** It is the state this season exists to leave.

**What is preserved unchanged:** no MCP tool, no gateway route and no ordinary
RPC method enables, disables or triggers semantic maintenance. `code.sem_config`
stays in the operator-uid table gated on `SO_PEERCRED`. Registering a repository
is still an operator act no model can perform, and it is the act that carries the
consent.

**Resource and security accounting.** Whether a daemon runs a compiler unasked
for a repository nobody has spoken about is a *root* decision:
`semantic_auto_default = ENABLED | DISABLED` in `/etc/atlas/system.conf`,
root-owned, no environment override, unrecognised value malformed. The
compiled-in fallback is a named constant, `ATLAS_SEM_AUTO_DEFAULT`, so a `memset`
produces "no statement" rather than a zero that happens to authorise a compiler.

**What it costs, plainly.** A model that can change a registered repository's
source can now cause a compiler to parse that source, where before it could only
do so for repositories an operator had enabled. The parse is bounded, sandboxed
and reads only; the cost is CPU and the writer thread's time.

## E. Legacy migration behaviour

`atlas_db_sem_config_set` always bound 0 or 1, so a stored `0` **cannot** be
distinguished from silence. Migration 19 does not invent the difference:

| stored | becomes | why |
| --- | --- | --- |
| `auto_rebuild = 1` | `ENABLED` / `OPERATOR` | only an operator ever wrote a 1 |
| `auto_rebuild = 0` | `UNSET` / `MIGRATION` | the unconditional default carries no information |
| no row | `UNSET` / `DEFAULT` | nobody has spoken |

The five distinctions §4 asks for are expressible after the migration and only
two of them are recoverable *from* it: explicit disable (`DISABLED`/`OPERATOR`,
only for rows written after A9.2.4), never configured (`UNSET`/`DEFAULT`), legacy
default (`UNSET`/`MIGRATION`), disabled due to failure (the governor's own
`fail_count`, which is a separate field and always was), and semantic unsupported
(`ATLAS_SEM_HOLD_NO_LIBCLANG`, also separate).

The conservative resolution is documented and tested: a migrated row reads
*migrated, intent unknown* and is decided by the policy. It never reads "operator
disabled", because that would be Atlas asserting a refusal nobody expressed — and
that refusal would then be honoured for ever, which is precisely what the intent
field exists to prevent.

## F. Build-input discovery architecture

```
registered repository
      ↓  bounded walk: root subtree, minus .git, minus operator exclusions,
      ↓  every descent openat(O_NOFOLLOW), within the limits.h ceilings
candidate discovery                    ∪  operator-pinned paths
      ↓
candidate validation
      regular file? not a symlink? within the size bound? parses as a
      compilation database? not already accepted under another path?
      ↓
canonical identity + dedup by (device, inode)
      ↓
accepted build descriptions            +  rejected ones, each with a reason
      ↓
TU inventory (per database; units keyed (source, config_digest))
      ↓
semantic generation + coverage manifest + sealed discovery verdict
```

Discovery is `src/sem/discover.c`, which opens no database handle, creates no
process, takes no lock and writes no row. Persisting a result is
`atlas_sem_discovery_run` in `src/sem/index.c`, one transaction; scheduling one is
the daemon's.

## G. Discovery completeness model

```
UNKNOWN   Atlas did not look, or looking failed, or the list was pinned by hand.
PARTIAL   Atlas looked and stopped early: a ceiling, an unreadable directory, or
          an operator exclusion.
COMPLETE  Atlas walked the whole bounded universe without reaching a ceiling.
```

`UNKNOWN` is zero. Only `COMPLETE` can support an absence.

Both dimensions §6 asks for exist, and neither is redundant with an existing one:
**BUILD_INPUT_DISCOVERY** is a new first-class coverage dimension (the twelfth) in
A9.2.2's existing vocabulary; **BUILD_INPUT_PROCESSING** is the generation's
existing unit counts — `tu_complete` / `tu_partial` / `tu_failed` /
`tu_unsupported` — which A8-CI already reports separately and never sums.

## H. The objective bounded-discovery contract

Atlas may say COMPLETE only about:

> the registered repository root subtree, excluding `.git`, excluding every
> operator-declared exclusion, not following any symlink, within
> `ATLAS_SEM_DISCOVERY_MAX_DEPTH` (12), `_MAX_ENTRIES` (400 000),
> `_MAX_CANDIDATES` (128) and `ATLAS_SEM_MAX_PATH_BYTES` (1024).

Every ceiling is reported when reached and makes the search PARTIAL. The universe
is reported beside the verdict — mode, candidate counts, exclusion list and the
walk's timestamp — so a reader never has to assume what was searched.

**Rejected alternative, recorded.** §7 lists "operator declaration of bounded
roots" as a completeness mechanism. It is rejected as a *completeness claim*
because the repository that produced this season is the counterexample: a
hand-written list of two databases, wrong, and no flag the operator could have
ticked would have made it right. MANUAL mode therefore reads UNKNOWN.

## I. Multiple-compdb support

Any number up to `ATLAS_SEM_MAX_COMPDBS` (32) accepted, `_MAX_CANDIDATES` (128)
considered. Tested at 0, 1, 2, 3 and 10 in `tests/test_sem_discovery.c`, with the
assertion being *the count that is on disk* at every step rather than any
particular number — the A9.2.3 defect where a second database silently vanished
is invisible at n = 1.

Ordering is deterministic by reported path, never by `readdir`, so two runs
produce one identity.

## J. Duplicate and overlap semantics

**Duplicates.** One file is one input however many paths reach it, deduplicated
by `(device, inode)`. A symlinked candidate is refused with
`a_symlinked_path_is_never_followed` and *shown*; the file it points at is
discovered on its own. The case is on disk in this repository: `/opt/atlas/compile_commands.json`
is a link into `build/`.

**Overlap — the same file in two databases.** Units are keyed
`UNIQUE(generation_id, source_text, config_digest)`, which predates this season.
Two compilations of one file under different `-D`s are therefore **two units**
and are not merged; `scope_covered` counts `DISTINCT source_text`, so one file
compiled twice is one covered source and coverage can never exceed the tree.
§10's requirement — do not silently merge semantically distinct compilation
contexts — is met by construction, and no policy had to be invented.

## K. Build-target and source classification

The denominator stays the one A9.2.3 established: the C sources and headers the
file index enumerates. A build-graph denominator is **not** invented, because
Atlas cannot state one.

What A9.2.4 adds is one operator-declared classification, `--vendor-root`.
Candidates under a declared vendor prefix are counted as `scope_excluded` and not
as uncovered — an operator saying "this subtree is somebody else's code" is a
classification, and treating it as a coverage failure would make every repository
with a vendored dependency permanently unable to state an absence about its own
code.

Test versus production classification is unchanged from A9.2.3: declared roots
only, matched on a path component boundary, and `test_scope_known = false` means
*Atlas does not know*, never *there are no tests*. Everything else is UNKNOWN
rather than assumed production.

**Capability limitation, stated:** the query surface still cannot ask
production-only caller questions. What it can do is refuse to claim
repository-wide coverage from production-only coverage, which is what §29 requires
and what `tu_test` / `tu_production` / `test_scope_known` carry.

## L. Discovery-change dirty tracking

```
accepted set + contents + verdict  →  atlas_sem_repo_discovery_identity
                                   →  atlas_sem_source_identity (domain v2)
                                   →  atlas_sem_freshness_of
                                   →  STALE, the_set_of_discovered_build_inputs_changed…
                                   →  atlas_sem_plan_for.should_build
                                   →  the A9.2.3 scheduler, unchanged
```

There is no second scheduler and no dirty bit. A database appearing,
disappearing or changing content moves the identity; a PARTIAL walk that later
completes moves it too, which is the only way a *sealed* manifest can be
upgraded.

The domain bumped to `atlas.sem.source-identity.v2`, so every pre-A9.2.4
generation is stale exactly once. That is the honest outcome: those generations
were built without knowing whether their input set was complete.

## M. Daemon auto-maintenance integration

Two sweeps on the watcher's timer, deliberately asymmetric:

| sweep | interval | cost |
| --- | --- | --- |
| freshness (A9.2.3) | 15 s | index reads + a digest over a handful of files |
| **discovery (A9.2.4)** | **300 s** | **a bounded directory walk** |

The split is what keeps correctness free of timing. An *edited* or *deleted*
database moves the identity at once, because content is digested on every
freshness read; only a *newly created* one waits for the next walk. Convergence,
not correctness.

Discovery is a writer-thread job (`ATLAS_JOB_SEM_DISCOVER`), coalesced against
the queue, and it considers every registered repository — including explicitly
disabled ones, because a repository nobody is building still deserves an honest
answer about what Atlas can see in it.

The freshness sweep now enumerates **registered** repositories rather than
configured ones. Enumerating the configured set would have made the new default
unreachable for exactly the repositories it exists for.

## N. Explicit operator disable

`code sem-config REPO --no-auto` records `auto_intent = DISABLED`,
`auto_intent_by = OPERATOR`. It is:

- checked **before** the effective boolean, so the reason names the person rather
  than the policy — `an_operator_explicitly_disabled_automatic_semantic_maintenance_for_this_repository`;
- reported as its own activity state, `EXPLICITLY_DISABLED`;
- never lifted by a policy change in either direction;
- distinct on every surface from `DISABLED` (policy default off), `NO_INPUTS`
  (nothing to build from), `FAILED` (the governor) and
  `this_atlas_was_built_without_libclang`.

## O. A9.2.2 negative-query integration

`ATLAS_COVDIM_BUILD_INPUT_DISCOVERY` is the twelfth coverage dimension. Every
negative verifier depends on it — `atlas.symbol_absent`, `atlas.proven_edge`,
`atlas.no_proven_caller` — because an undiscovered compilation database could
name the source that defines the symbol. `atlas.content_hash` does not, because
it reads a file rather than an index.

The fold is in `coverage_is_complete`: a generation whose recorded `discovery` is
not COMPLETE is not coverage-complete, whatever else is true of it. Where
discovery is UNKNOWN or PARTIAL a negative result is `UNAVAILABLE` and the truth
stays `UNKNOWN`, never `ABSENT`.

A9.2.2 is not weakened. It gains one more way to be honest.

## P. A9.2.3 freshness integration

Nothing about the freshness model changed. What changed is one of its inputs and
one of its reasons:

- `atlas_sem_repo_compdb_digest` now digests the **accepted** set rather than the
  pinned one, so the specific `a_compilation_database_changed…` reason still
  fires for a discovered database's contents.
- A new reason, `the_set_of_discovered_build_inputs_changed_since_this_index_was_built`,
  is ordered *after* every specific check and *before* the broadest one, so an
  operator is told what happened in the most useful terms available rather than
  being sent to look at their source.
- `atlas_sem_freshness_now` is still the one implementation of the freshness
  question, and now gathers every live fact in a **single pass**
  (`live_facts`) — the compilation databases feed two digests, and reading them
  twice would have reintroduced the exact defect A9.2.3's closure measured and
  fixed.

## Q. CLI / RPC / MCP / Mission Control

One shape on every surface. The derived state travels as the same keys from the
CLI's `--json`, `sem.status`, the gateway route and MCP:

`activity`, `hold_reason`, `auto_intent`, `auto_intent_by`, `policy_default`,
`discovery`, `discovery_mode`, `generation_discovery`, `inputs_accepted`,
`inputs_rejected`, `discovered_at`, `discovery_limit`, `build_inputs[]` (path,
origin, accepted, reject_reason, digest, units), `compdbs[]`, `test_roots[]`,
`excludes[]`, `vendor_roots[]`, and the generation's `discovery` / `input_count` /
`scope_excluded`.

`discovery_limit` names **which ceiling** stopped a walk, and it is on every
surface for A8-CI's reason: a PARTIAL verdict without it tells somebody a search
was cut short without saying where.

Every one of those keys is written in `src/ipc/server_sem.c` **and** read back in
`src/core/service_remote.c`. Writing one without reading it back is how the
socket path and the local path start disagreeing, which is the defect every
season since A9.2.1 has had to name once.

New CLI flags: `--exclude`, `--no-excludes`, `--vendor-root`,
`--no-vendor-roots`, `--discover`, `--no-discover`. `--compdb` became optional on
`code index`.

Mission Control shows discovery as its own rows and the candidate list as a
table, with rejected candidates and their reasons. It never shows a green
COMPLETE badge over an UNKNOWN discovery.

**No new RPC method and no new MCP tool.** `sem.status` already carries the whole
derived state as a read, so §30 is satisfied without growing the surface that has
to be defended.

## R. Security

| attempt | outcome |
| --- | --- |
| model declares discovery COMPLETE | no field on any reachable method carries a discovery state inward; `discovery_state` is written only by `atlas_sem_discovery_run` |
| model inserts a compdb outside repository scope | the walk never leaves the root; a pinned path is resolved component-by-component with `O_NOFOLLOW` and refused outside |
| model marks activity enabled | `code.sem_config` is operator-uid only; every other peer gets `unknown method` |
| model clears an explicit operator disable | same gate; and no other method writes `auto_intent` |
| model marks semantic CURRENT | freshness is derived on every read and never stored |
| model forges a build-input identity | the identity is computed from files Atlas reads itself |
| rebuild storms | one build per repository at a time (`atlas_writer_sem_index_pending`), coalescing, and the retry governor comparing identities rather than elapsed time |
| operating on an unauthorised repository | `NOT_REGISTERED`, from the registry, without looking at the filesystem |

Every plausible verb name — `sem.discover`, `code.discover`, `sem.enable`,
`sem.set_discovery`, `sem.compdb_add`, `sem.mark_complete`, `sem.mark_current`,
`sem.build_inputs_set` and eight more — is in the negative enumeration in
`tests/test_orch_rpc.c` and answers `unknown method` to an ordinary peer.
`tests/test_sem_auto.c` drives the refusal **through the real transport** against
a live daemon and additionally asserts that the refused request recorded no
operator intent.

## S. Backup / restore

`scripts/a924-backup-check.sh`, against an isolated data directory and an
isolated fixture repository — it never opens the machine's real index and never
stops a service. **13 checks, 0 failed.**

The fixture is built to make the check mean something: two good compilation
databases, one malformed one *inside* the searched universe (so it is refused
rather than skipped), one excluded subtree (so the search is genuinely PARTIAL),
a declared vendor root, and an explicit operator disable.

| Preserved across backup → restore | Why it matters |
| --- | --- |
| `auto_intent = DISABLED` | a restore that lost it would silently re-enable a repository somebody disabled |
| `auto_intent_by = OPERATOR` | a restore that lost the provenance would make a decision look like a default |
| `activity = EXPLICITLY_DISABLED` | the derived state agrees on the other side |
| `inputs_accepted = 2` | a restored index reporting fewer inputs is a wrong search, not a smaller one |
| `discovery = PARTIAL` | a restore that lost the verdict would turn a bounded claim into UNKNOWN and stop every negative conclusion |
| the rejected candidate **and its reason** | a candidate nobody is shown is indistinguishable from one that does not exist |
| `source_identity` byte-identical | the daemon resumes rather than rebuilding from nothing |

The backup itself was created and verified through the ordinary A5 path, so the
new tables carry no special handling — which is the point: migration 19 is
additive and `sem_build_inputs` is an ordinary table.

## T. Performance

`scripts/perf-a924.sh REPO [BASELINE]`, against the installed binary and the
running daemon. It follows the discipline every `perf-*.sh` here follows: it
**asserts its own floors and its own limits and exits non-zero** rather than
printing numbers nobody checks, and it refuses to measure a repository with no
accepted build input or fewer than 100 candidate sources — shrinking the fixture
to make a run pass is the one failure mode a performance gate cannot detect about
itself.

The limits are **required bounds, not observations**.

| Measurement | Limit | atlas (1 input, 203 units, 202 sources) | dna (3 inputs, 775 units, 766 sources) |
| --- | --- | --- | --- |
| `code sem-status --json` | under 100 ms | **28 ms observed** | **41 ms observed** |
| one bounded discovery walk | under 5 000 ms | **49 ms observed** | **751 ms observed** |
| baseline: a repository with no build description | — | 23 ms observed | 23 ms observed |

Report those as observations. "41 ms observed", never "under 41 ms", which reads
as a bound Atlas does not hold.

**What the numbers say.** A status read costs 5 ms over the baseline on a
one-database repository and 18 ms on a three-database one, which is the live
digesting of the accepted databases and nothing else — the consolidation into
`live_facts` is why it is not double that. The walk is the expensive thing this
season adds, and 751 ms over a 20 000-file repository is what fixes the interval
constant at 300 s rather than at 15 s: it is cheap enough to run unattended and
far too expensive to run on every status read, which is exactly why membership is
persisted and only content is read live.

**Semantic index durations, observed on the converged repositories:**

| | first automatic build | incremental rebuild |
| --- | --- | --- |
| atlas — 1 database, 203 units | 254 s | **30 s** |
| dna — 3 databases, 775 units | 235 s | 170 s |

The incremental figure is unit reuse doing its job: an edit that does not change
a widely-included header reparses a fraction of the tree. It is also why
limitation AA-4 is about the *first* build — steady state is not the problem.

**Periodic reconciliation does not become an expensive recursive scan.** The
15-second freshness sweep does no walking at all: it reads the persisted
candidate list and digests the accepted files. The walk runs on its own 300 s
timer, is coalesced against the writer queue so a backlog cannot accumulate, and
costs 751 ms on the largest repository here.

### What the installed system found that no fixture did

Two defects were caught by running the real thing, and both are the kind a
fixture cannot produce.

**1. A PARTIAL search with no reason.** After the cutover, `/opt/atlas` reported
`discovery = PARTIAL` and `discovery_limit` empty. The cause was correct
behaviour — the daemon runs as `atlasd`, and `/opt/atlas/.cache` is not readable
by it, so the walk genuinely could not account for that subtree. But *nothing
said so*: a ceiling recorded a reason and an obstacle did not, which is the same
"a hole nobody can see" failure this season exists to end, one layer down.
`note_partial` now records a reason at every PARTIAL site — a ceiling, a
directory that could not be entered, one that could not be read to the end, an
allocation failure, and an operator's own exclusion — and the field is reported
on every surface as *incomplete because*.

**2. An exclusion silently abandoned the rest of the walk.** Fixing (1) exposed
it immediately: `limit_reached` was doing two jobs — "record why this is
PARTIAL" and "stop walking" — so recording a reason for an ordinary `--exclude`
made the walk skip every sibling directory it had not yet visited. The search
returned PARTIAL, which was true, and found one compilation database where two
existed, which is exactly the outcome the season exists to prevent. The two jobs
are now separate fields: `stop` is set only by the two ceilings that bound
*total* work (entries read, candidates found), and every per-branch limit records
its reason and carries on. `test_sem_discovery` pins it.

**3. Three manifest fields never crossed any surface.** `discovery`,
`input_count` and `scope_excluded` were added to `sem_generations`, written at
publication and read back into the struct — and put on *nothing that reports a
generation*. `code sem-status --json` answered without them, on the local path
and over the socket alike. This is the exact drift the "Extending A9.2.3 safely"
checklist warns about, in a checklist this season itself extended, and it was
found by reading a real generation rather than by any test. Fixed on all four
surfaces, and `test_sem_auto` now enumerates **every** key the season adds and
requires each to cross the socket — so the next omission fails a test rather
than being noticed by somebody looking.

**4. The call graph decayed on every incremental rebuild.** The worst of the
four, and it is an **A8-CI defect that A9.2.4 made harmful rather than one this
season introduced.**

`atlas_db_sem_copy_unit` carried `sem_edges.unit_id` across verbatim, so every
edge a reused unit contributed pointed at a unit row belonging to the *ancestor*
generation. Nothing failed at the time. What failed was the pass after that: it
selects the edges to carry by joining `sem_units`, and once the ancestor's rows
were pruned the join found nothing. Each incremental pass therefore carried
fewer edges than the one before.

Measured on the acceptance repository, from the daemon's own index:

| generation | units | symbols | edges | reused units |
| --- | --- | --- | --- | --- |
| full build | 775 | 26 958 | **475 741** | 27 |
| four incrementals later | 775 | 26 961 | **10 631** | 756 |

Of those 10 631 edges, **3 479 referenced unit rows that no longer existed**.
The symbol count was untouched throughout, which is why nothing looked wrong: a
symbol lookup answered correctly while the call graph underneath it was emptying.

It had been latent since A8-CI and was unreachable in practice, because nothing
rebuilt automatically — the repositories that would have decayed were never
rebuilt at all. A9.2.4 makes automatic maintenance the default, which turns it
into a graph that quietly empties itself, so the fix belongs to this season even
though the defect does not.

**The fix, and why it is three changes rather than one:**

1. **Write the unit row before its facts.** An edge belongs to the unit that
   produced it, and a carried edge must belong to the row in *this* generation —
   so that row has to exist before the copy can name it. The old ordering made
   that impossible, which is why the copy carried the ancestor's id instead.
2. **Look the unit id up rather than take `sqlite3_last_insert_rowid`.** The
   write is an upsert, and on the DO UPDATE branch nothing is inserted — so the
   rowid would be some other table's, and a wrong one here would attach a unit's
   edges to a different unit silently, on the replay path a crash produces.
3. **Bump `ATLAS_SEM_ANALYZER_VERSION` to 2.** Identical bytes now produce a
   different — and correct — graph, which is exactly the condition the epoch
   exists for. It is also the repair: nothing short of a full rebuild restores a
   graph that has already decayed, and a stale epoch is what makes the daemon
   rebuild every affected repository once, without anybody having to know which
   they are.

`tests/test_sem.c` pins both halves — no edge may reference a unit outside its
own generation, and an incremental generation must not lose most of its edges —
and the assertion was verified to be load-bearing by reverting the fix and
watching it fail with *"3 carried-forward edges reference a unit outside their
own generation"*.

**5. The analyzer epoch was unenforceable.** Found while verifying that (4)'s
repair actually worked — it did not.

A3's rule, inherited by A8-CI: bump `ATLAS_SEM_ANALYZER_VERSION` whenever a pass
would produce different facts from identical bytes, and the next pass rebuilds.
The first half worked: a bumped version makes a generation STALE and schedules a
rebuild. The second half did not. A unit's input digest covered its include
closure's *content* and the compilation flags, and **nothing about the producer**
— so the rebuild found every unit unchanged, carried the old analyzer's facts
forward, and republished them under the new version.

Observed directly: after bumping to 2 to repair (4), the scheduled rebuild of a
203-unit repository **reused 203 of 203 units** and republished the same decayed
graph with `analyzer_version = 2` on it.

That makes every analyzer bump in Atlas' history a no-op for any repository
nobody rebuilt from nothing by hand — which, before automatic maintenance, was
most of them. The compiler version had the same hole: `atlas_sem_freshness_of`
treats a changed compiler as stale, and that staleness was equally unenforceable.

The fix is one line of substance: `input_digest` folds in the analyzer id, the
analyzer version and the compiler version, and its domain bumps to
`atlas.sem.unit.v2`. A machine upgrading from A9.2.3 now gets the repair for
free — its generations carry `analyzer_version = 1`, so they are stale, and their
stored unit digests carry the v1 domain, so nothing is reused and every unit is
reparsed.

There is **no unit test for this one**, and that is stated rather than papered
over: exercising it needs two analyzer versions in one process. A placeholder
test that asserted the digest is hex was written and deleted — a test that cannot
fail is worse than none, because it reads as coverage. What stands in its place
is the observation below, the comment at the call site, and the fact that the
first thing anyone bumping the epoch will do is watch a rebuild.

**6. `code index` reported "parsed 0, reused 0" on every deployed machine.** The
remote form reads its summary from the published generation — deliberately, so
the local and socket paths cannot describe one index differently — and a
generation records the rows it holds rather than the work the pass did, which is
A8-CI's closure and is right. The two pass counters therefore had nowhere to come
from. Under A7.1 the socket is the operator's only path, so that was the only
report there was. They now ride on the operation's detail line, which is what it
is for.

## AA. Remaining limitations

Stated rather than implied, and each with what it would take to remove.

1. **A source no discovered compilation database names is invisible to every
   coverage dimension.** Atlas answers from the build descriptions it can find.
   Removing this needs build-system integration, which is a different phase's
   argument.
2. **Target class is UNKNOWN beyond declared test and vendor roots.** A
   compilation database does not say which target a unit belongs to; the `-o`
   path often encodes it, and inferring a class from a path shape is the guessing
   `--test-root` exists to avoid. The consequence is that the query surface still
   cannot ask production-only caller questions — but coverage never claims
   repository-wide semantics from production-only coverage.
3. **A newly created compilation database is noticed at the next discovery pass**,
   not immediately — up to `ATLAS_SEM_DISCOVERY_INTERVAL_MS` (300 s). Edits and
   deletions are immediate, because content is digested on every freshness read.
   Convergence, not correctness.
4. **Semantic indexing occupies the writer thread.** This is A8-CI's design and
   A9.2.4 does not change it, but the default-on policy increases exposure: a
   repository with several build configurations can occupy the writer for
   minutes, during which no other write to the index proceeds. The mitigations
   that exist are real — one build per repository at a time, coalescing, the
   retry governor, unit reuse across generations — and none of them shortens a
   first build. **Worth a backlog line:** moving semantic indexing off the writer
   thread, or yielding between units, is the fix, and neither belongs in this
   season.
5. **`MANUAL` discovery can never support an absence**, by design. An operator who
   genuinely must pin an exact list gives up negative conclusions about that
   repository. The alternative — an operator-asserted completeness flag — is
   rejected in §H with the counterexample.
6. **Discovery does not observe a running system.** A9.2.2's rule is unchanged:
   `runtime_state` and `deployed_config` are UNKNOWN for every verifier, so
   repository absence never becomes operational absence.
7. **`dirs_visited` and `entries_seen` are computed but not persisted.** The walk
   reports which *ceiling* stopped it, which is what an operator acts on; the raw
   traversal counts exist only in the in-memory result and the daemon log. If a
   future phase wants the universe quantified rather than described, they are the
   two numbers to persist.

## A note on verifying an install, which A9.2.1's rule got half right

A9.2.1's closure found `make install` reporting `-- Up-to-date:` while the
installed file differed from `build/atlas`, and wrote the rule: **use `cmp`
rather than the report.** That is right about not trusting the report and wrong
about `cmp` being the test.

`cmake --install` **strips the RUNPATH** from the installed copy. On this machine
that is a 116-byte difference at offset 8971 — `Library runpath:
[/usr/lib/llvm-14/lib:]` zeroed — so `cmp` reports a difference on every correct
install, for ever, and an operator who follows the rule learns to ignore it.

The value that answers the actual question is the **GNU build-id**, which is a
hash of the compiled code and is unaffected by a post-link RPATH edit:

```
readelf -n build/atlas          | grep "Build ID:"
readelf -n /usr/local/bin/atlas | grep "Build ID:"
```

Both read `932ecf714392667b184cce2264f1ca341aa765f2` for the shipped build, so the
installed binary is the tested one. `cmp` remains useful for what it can still
say — the two files are the same *size* and differ only where the loader
metadata is — but the equality check is the build-id.

The rest of A9.2.1's rule stands unchanged and was applied: both services were
restarted, and `readlink /proc/<MainPID>/exe` reports `/usr/local/bin/atlas` for
each with no `(deleted)` suffix. `atlas-dispatcher` is restarted too, because it
runs the same binary and would otherwise keep executing the previous inode.

libclang still resolves after the RUNPATH strip (`libclang-14.so.13` is on the
default search path), which is checked rather than assumed: the daemon reports
`libclang_available: true` and the compiler version it will use.

## Operator decisions recorded during this season

Two configuration choices were made on this machine. Both are **operator
decisions**, not product logic, and neither names a repository anywhere in the
Atlas source.

**1. `/opt/atlas` excludes its sanitizer and debug build trees.**

The repository holds five real compilation databases — `build/`, `build-debug/`,
`build-asan/`, `build-ubsan/`, `build-tsan/` — describing the same ~198 sources
under different `-D`s, plus a top-level `compile_commands.json` symlink into
`build/`. Discovery accepts all five, and it is right to: they are five genuinely
distinct compilation contexts and merging them would be the thing §10 forbids.
The cost is real — five configurations × 198 units, against a measured 235 s for
one configuration — and semantic indexing runs on the writer thread, so the first
build would occupy it for a long time.

The knob is `--exclude`, and it is used:

```
atlas code sem-config atlas --exclude build-debug --exclude build-asan \
                            --exclude build-ubsan --exclude build-tsan
```

The honest consequence is recorded rather than hidden: `/opt/atlas`'s discovery
is therefore **PARTIAL**, so Atlas can never state an absence about its own code
until the exclusions are lifted. That is correct — an operator who says "do not
look there" has left a hole in the universe, and Atlas says so.

**2. `/opt/dna` is left alone.**

Its stored `auto_rebuild = 0` migrates to `UNSET` / `MIGRATION`, so the
root-owned default decides, and the default is ENABLED. The first discovery sweep
therefore finds all three of its compilation databases — including the one that
was never configured — and the daemon rebuilds. **That is the product working**,
and it is the empirical answer to §39's last question.

It is stated rather than allowed to happen quietly because it has a cost: DNA is
under active development, the rebuild occupies the writer thread, and §39 asks
that this season not disrupt that. The rebuild is one-off and bounded (the
previous full pass took 144 s for two databases). An operator who does not want
it writes `atlas code sem-config dna --no-auto`, which is honoured for ever.
No DNA file was written by this season — see AB.

## Answers to §40 — the product decisions

**1. Should semantic auto-maintenance be default-on?** Yes, with a root-owned
machine-wide override and a per-repository operator refusal that no default
overrules. The product rule the season exists for — maintenance must not depend
on somebody remembering — cannot be satisfied by any opt-in shape, and the thing
the opt-in was protecting was never code execution.

**2. What counts as an explicit operator disable?** `auto_intent = DISABLED`
with `auto_intent_by = OPERATOR`, written only by `code sem-config --no-auto`
through the operator-uid path. Nothing else can produce it, no default overrules
it, and migration 19 never manufactures one from a value that carried no
information.

**3. How does Atlas know build-input discovery is complete?** It does not know it
in general and never claims to. It walks a **bounded search universe** it can
name — the repository root, minus `.git`, minus declared exclusions, within
stated ceilings — and says COMPLETE about that universe and nothing wider, with
the universe reported beside the verdict. DID NOT DISCOVER is not PROVEN NOT TO
EXIST.

**4. What does it do when completeness cannot be proven?** Reports `PARTIAL` or
`UNKNOWN` with the reason, and refuses every negative conclusion that would rest
on it: `ATLAS_COVDIM_BUILD_INPUT_DISCOVERY` becomes insufficient, `settle()`
returns `UNAVAILABLE` rather than `FAIL`, and the truth axis stays `UNKNOWN`
rather than becoming `ABSENT`. Positive conclusions are unaffected, because an
incomplete search cannot conjure a symbol that is not there.

**5. How are multiple compdbs discovered?** One bounded walk, `openat` with
`O_NOFOLLOW` at every descent, matching the fixed filename
`compile_commands.json`, deduplicated by `(device, inode)`, ordered
deterministically by reported path, up to 128 candidates and 32 accepted, with
every rejection recorded and shown. Operator-pinned paths are accepted in
addition, and are marked `BOTH` when the walk finds them too.

**6. What happens when a new compdb appears?** The next discovery pass accepts
it; the accepted set changes; `atlas_sem_repo_discovery_identity` moves;
`atlas_sem_source_identity` moves; freshness reports
`the_set_of_discovered_build_inputs_changed_since_this_index_was_built`; the plan
says `should_build`; the A9.2.3 scheduler rebuilds. No second scheduler, no dirty
bit, and nobody has to run a command.

**7. What happens to negative knowledge while discovery is incomplete?** It is
`UNKNOWN`, and stays `UNKNOWN` until the search is COMPLETE. This is strictly
more conservative than A9.2.2, never less: a generation that could previously
support an absence can now be refused one, and none that was refused can now be
granted one.

**8. Why did DNA expose the issue?** Because it is the only repository on this
machine with more than one build tree *and* a hand-written build description. A
single-database repository cannot exhibit either defect — the activation default
looks like a deliberate choice and the missing third database does not exist —
which is exactly why every fixture in the suite missed both and a real workload
found them in a day.
